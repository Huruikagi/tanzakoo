# Tanzakoo — 壁打ちメモ

## 現在の合意済みの実装方針

ユーザーの「他は推奨してくれたやつでいい」により、以下を採用する。後段に残る過去の推奨案・検討履歴より、この節を優先する。

- 初版からTauri 2 + React + TypeScript + Rustを使う。
- ローカル利用を前提に、画面とRustの処理を分離する。ブラウザ版の同時提供は初版に含めない。
- CodexとClaudeを対応対象とし、ACPと既存アダプターを軸に接続を検証する。
- 各自の契約アカウントでの利用を優先する。実際の認証・契約対応は接続検証で確認する。
- 初版は必要なエージェント環境を導入・ログイン済みである前提で始める。
- 会話開始時にエージェントを選ぶ。会話途中の切り替えや履歴移植は後から検討する。
- 小さな初版で、会話・自動起票・カード参照・変更提案と承認・ローカル保存の往復を試す。
- 両エージェントの最小接続を早めに確認し、自動並べ替え等は基本操作の後に検討する。
- 必要な依存関係を積極的に利用する。追加前に名前・用途・理由を伝え、通常はその説明後に進める。詳細は `AGENTS.md` を参照。
- Node.jsとpnpmはmiseで管理する。lint・整形はBiomeまたはOxlint / Oxfmtを使う（ESLint + Prettier案は撤回）。`@shadcn/lint` も採用候補とし、現時点の推奨はOxlint + Oxfmtとの組み合わせ。

## 目指すもの

曖昧なプロダクトアイデアを、AIとの対話とカード操作によって実装可能な要求へ収束させるローカルツール。

## ユーザーが示した方針

- 1枚のカードで1つの議論のトピックを扱う。
- チャット履歴ではなく、ボードを正とする。
- AIが変更を提案し、ユーザーが承認する。
- 最初はCodexをACP経由で利用する。
- Local-first。

## 追加で確認できた方針

- UIはカンバンボードのようなイメージ。
- AIによる論点カードの起票は自動で行う。
- 起票されたカードをすべて片付ける必要はない。
- 候補欄は「あとで拾えるアイデアの山」に近い。候補を蓄積する方向。
- 今の会話に合わせて候補の順番が変わることは許容できそう、というユーザーの意向。具体的な並べ替えルールは未決。
- 自動起票は、当初の「AIが変更を提案し、ユーザーが承認する」原則の例外として明確になった。その他の変更の承認範囲は引き続き検討する。

以前ユーザーから挙がった選択肢：

- 不要なカードを簡単に消せる。
- 検討のボードに上げなかったカードは、何らかのトリガーで自動的に消える。

その後、「あとで拾えるアイデアの山」として残す方向になったため、自動消去は現時点の基本案に含めない。手動で消す方法は未決。

整理案（AIからの提案・未合意）：

- 自動起票される「候補」と、ユーザーが選んだ「検討する」以降を区別する。
- 候補はワンクリックで非表示にでき、取り消せる。
- 候補は残したまま、会話との関連度に応じて候補列内の表示順を変える。
- 並べ替えは会話の区切りで行い、ユーザーがカードを操作している最中には動かさない。
- 候補列内の表示順と、列をまたぐ状態変更は分ける。自動で手前に来たことは、ユーザーが検討対象に選んだことを意味しない。

## 入口のイメージ

最初からカードを選ぶのではなく、サイドバーのチャットで自由に話し始める。

例：「TODOアプリ作りたい」と伝えると、エージェントが「Webなのかアプリなのか」「リマインダーは必要か」など、検討したいことをカードとして起票していく。

当初の基本ループ：

Idea → AIが議論カードを提案 → ユーザーがカードを選ぶ → エージェントと議論 → エージェントがボード変更を提案 → ユーザーが適用

入口についての補足を反映した整理案（未合意）：

自由なチャット → 論点がカードとして現れる → 必要な論点を選んで掘り下げる → 結論をボードに反映する

## 次に話したいこと

- 不要な候補を手動で消す方法。
- 会話に応じた候補の並べ替えタイミングと、ユーザーによる順序指定との関係。
- 議論中の論点と、合意済みの要求をボード上でどう表すか。

## 作業領域とチャットの往復

確認できた基本構成：メイン画面は「ボード」「カード詳細」「チャット」の大きく3領域で構成する。各領域の配置や開閉方法は未決。

ユーザーが示した体験の参考：

- Windsurfのように、サイドペインのチャットからエージェントに指示すると、作業対象がエディタのタブで開く体験に近いもの。
- コードの範囲選択をチャットに参照として送る操作のように、ボード上の内容を指して会話できる。
- これはユーザーが示した操作の比喩であり、参考製品の現行仕様や名称を確認した記録ではない。

Tanzakooへの対応案（AIからの提案・未合意）：

- ボードと個別カードの詳細を行き来できる。タブ方式にするか、並べて表示するかは未決。
- エージェントが起票・変更提案した対象を、作業領域で確認できる。大量の起票でタブが増えすぎないよう、開く対象のルールは別途検討する。
- カード全体、カード本文の選択範囲、複数カードをチャットに参照として添付できる。
- チャットでの参照と、変更対象の指定・変更承認は区別する。
- カードを切り替えてもサイドペインの会話を続けられる形を出発点とする。会話を分ける仕組みは未決。
- ボードで見渡す → カードを開いて読む → 内容を指して話す → 変更提案を確認・適用する、という往復を支える。

## 初版の範囲

これ以上の詳細仕様を広く固める前に、実際の操作で中核の往復を試せる小さな初版を作る。

- ボード・カード詳細・チャットの3領域。
- チャットからAIが候補カードを自動起票し、候補をローカルに保存する。
- カードを選んで詳細を開き、カード全体または本文の選択範囲をチャットへ参照として渡す。
- AIの本文変更提案を確認し、適用または却下する。
- 候補を検討対象に移す操作と、不要なカードを消す操作。

会話に応じた自動並べ替え、類似カードの自動整理、複雑な状態や複数会話の管理は、基本操作を試した後に検討する案。

実装時は、エージェントとの接続と、起票・変更提案をアプリで受け取る経路を早めに確認する。採用する技術構成は冒頭の合意済み方針を参照。

このメモは壁打ちの記録であり、確定した仕様ではない。

## 実行環境・技術構成の相談履歴

ユーザーの意向：

- まずローカル環境で使う。
- ローカルWebアプリから始め、必要ならTauriに載せられるRust + TypeScript（React）を候補に挙げた。
- 最初からTauriで始める案も検討し、その後に採用した（冒頭参照）。

採用したAIの推奨案：

- 初版からTauri 2 + React + TypeScript + Rustを使う。
- ローカルエージェントのプロセス管理と保存処理が必要なため、Rust側にその役割を置く。ブラウザ版用のHTTPサーバーは必要になってから検討する。
- Reactは3領域のUI、参照の選択、変更提案の表示を担当する。
- Rustのボード操作・保存・エージェント接続処理はTauriのコマンド受付から分離し、React側もTauri呼び出しを窓口にまとめる。
- この分離は将来の移植を容易にするためのもので、初版でブラウザ版も同時提供することを意味しない。
- Windowsの開発にはMicrosoft C++ Build ToolsとWebView2等が必要。現在のPCで充足しているかは未確認。
- ACPによる実際の接続経路は別途確認が必要。Tauriを選ぶだけで接続が成立するわけではない。

確認した公式資料：

- [Tauriの前提条件](https://v2.tauri.app/start/prerequisites/)
- [外部バイナリの埋め込み](https://v2.tauri.app/ja/develop/sidecar/)

## エージェント接続で決めること

ユーザーは接続技術の詳細には詳しくなく、自分が判断すべきポイントを確認したい。

追加で確認できた要求：

- Claudeも対応対象に含めたい。会社ではClaude利用者が多い。
- ユーザー本人もClaudeを契約しており、必要に応じて動作検証やClaude側への調査依頼に協力できる。
- この発言は、今すぐClaudeを起動して調査を送信する依頼ではない。
- Claudeの具体的な利用形態・契約プランは未確認。接続先としてはClaude Code系のACPアダプターを想定して調査する案。

利用体験についての相談履歴（結論は冒頭参照）：

- Codexに加えてClaudeへの対応も要求されたため、複数エージェントへの対応を前提に接続方式を検討する。初版に含める具体的な対応範囲・順序は未決。
- 自分のChatGPTアカウントによるCodex利用を優先するか、APIキーによる従量課金を前提にするか。推奨案は前者。
- 初版では利用者がCodex CLIを導入・ログイン済みである前提を許容するか。推奨案はこの前提で始め、アプリ内セットアップは後から整える。

実装側で調査・設計すること：

- ACPの具体的な接続実装、対応機能、Windowsでの起動・終了・再接続。
- 会話の返答と「候補の作成」「既存カードの変更提案」を構造化した別の操作として受け取る経路。
- 既存カードの変更はアプリ側で承認待ちとして保持し、ユーザーが適用したときに確定する。接続方式自体に承認ルールの保証を委ねない。

公式資料から確認できたこと：

- Codexには、自作アプリへ認証・会話履歴・承認・ストリームイベントを組み込むためのApp Serverという接続口もある。
- CodexはChatGPTサインインによる利用と、APIキーによる従量課金の両方に対応する。選択した接続実装での利用可否は検証する。
- これらはACPの対応状況を検証した結果ではない。当初のACP方針は変更しておらず、App Serverは比較候補。

資料：

- [Codex App Server](https://learn.chatgpt.com/docs/app-server)
- [Codexの認証](https://learn.chatgpt.com/docs/auth)

Claude対応を踏まえた採用方針と検証事項：

- 当初のACP方針を軸に、共通のACPクライアントからCodex用・Claude用の既存アダプターへ接続する構成を検証する。
- Zedの現行公式資料では、CodexとClaude AgentがACP経由の外部エージェントとして案内されている。Tanzakooでの動作を検証済みという意味ではない。
- UIを作り込む前に、両方で「ログインして会話」「候補を起票」「変更提案をアプリに返す」の最小経路を確認する。
- 接続・認証・対応機能の差はアダプターごとに確認し、ボードの操作と承認ルールはTanzakooが共通で保持する。
- 初版の操作案は、会話を始めるときに利用するエージェントを選ぶ形。同じ会話の途中での切替・履歴移植は別途検討する。
- ユーザーへClaude側の検証を依頼する場合は、起動方法・確認操作・期待する結果をまとめた具体的な手順を用意する。
